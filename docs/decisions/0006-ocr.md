# 0006 — OCR as a fallback, local-only for now

**Status:** Accepted (`5ff9fdb`, `c3d288f`, `0efdf4a`, `4bcdec8`). The latest
rewrite is restored in this handover branch, with logging adapted from `967d1d4`.
See [known issues](../known-issues.md) for resource and recovery limitations.

## Context
Some client deeds are scanned and have no text layer. A survey of 32 documents found
only one real client document with no text at all: the Powell trust deed, 4 pages.

## Current implementation
- Extract with pdfplumber first. OCR runs only when the text layer is thin. It is not
  decided up front, because OCR takes minutes per document and replaces the whole text.
- OCR is PaddleOCR PP-StructureV3 with a confidence check. Low-confidence pages go to
  a vision model through Ollama (`qwen3-vl`, set with `OLLAMA_VLM_MODEL`), prompted to
  return tables as markdown.
- The LLM cleanup pass is off (`cleanup=False`). It is too slow on CPU and retrieval
  doesn't need it.
- Historical client-VM guidance was `OCR_ENABLED=false`: PP-StructureV3 crashed in paddlepaddle 3.3.1's
  oneDNN kernel there, and the vision model needs about 5.4 GB, which got Ollama killed
  for running out of memory on the 7.8 GB host.
- OCR packages are imported lazily, so the app runs without them.

## Consequences
- If OCR is disabled and PDF extraction yields no text, ingestion reports failure.
  Current VM flags and native OCR execution have not been reverified.
- OCR takes about 20–40 minutes for a 12–57 page deed, so it suits batch ingestion,
  not interactive use.
- Future work: OCR only the thin pages, or use a larger host or GPU.
